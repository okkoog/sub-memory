# 兼容性说明（Pen的委托UI优化 / `Pen_mod_Request_UI`）

本文写给**其它 mod 的作者**，说明三件事：

1. 本 mod 会**识别**面板上的哪些东西（代码级判定）；
2. 本 mod 提供哪些**可调用接口**；
3. 想和本 mod 共存时，**怎么写才能在没有本 mod 的存档里仍然保持原版表现**。

> 本 mod 接管的是原版「市场 → 委托」面板：自建双列网格与滚动、左侧来源/派系筛选栏、把第三方委托渲染成原版样式的卡片。
> 关闭本 mod 时会把面板完整还原为原版（详见第 7 节）。

---

## 一、总览

面板上的卡片分三类：

| 类别 | 判定 | 本 mod 的处理 |
|---|---|---|
| **原版物品委托卡** | `StoreRequestElement` 且 `storeRequest != null` | 搬进单元格 `rb_cell`、加装饰（奖励/预览/临期）、按派系筛选、计入「可完成」 |
| **框架委托卡** | 由本 mod 依据注册信息渲染，名字前缀 `rb_fw_`，带 `FrameworkCard` 组件 | 由本 mod 全权负责（内容、按钮、点击） |
| **外来卡** | `StoreRequestElement` 且 `storeRequest == null` 且**没有** `FrameworkCard` | **不包裹、不筛选、不计数**；它们所在的 `PCUIManager.gridLayout` 已被设为「隐形数据区」，因此**不会显示** |

「隐形数据区」是本 mod 的关键行为：接管面板时给原版 `gridLayout` 挂
`CanvasGroup { alpha = 0, blocksRaycasts = false, interactable = false }`，
所有可见卡片都渲染在本 mod 自建的 `rb_content` 里。

---

## 二、本 mod 能识别什么

### 1. 原版物品委托卡
- 组件：`StoreRequestElement`；
- `storeRequest != null`；
- 这些卡由游戏 `PCUIManager.OnChange` 创建，本 mod 只把它们重新挂到自己的单元格里（不改数据、不改交付逻辑）。

### 2. 框架委托卡（本 mod 自己渲染的）
- GameObject 名字前缀：`rb_fw_`；
- 组件：`FrameworkCard`，字段 `Key / CommissionId / FactionId / SourceId / SourceName`；
- **适配器扫描面板时必须跳过它们**，否则会把本 mod 渲染的卡当成外来卡再抓一遍。

### 3. 外来卡
同时满足：
- 组件 `StoreRequestElement`；
- `storeRequest == null`；
- 不含 `FrameworkCard`。

处理：**不包裹、不筛选、不计数**，交给它自己的作者。由于 `gridLayout` 是隐形数据区，这类卡不会显示在界面上。

> 结论：想在本 mod 的界面里显示卡片，请走第 3 节的接口（框架委托），不要往 `gridLayout` 里塞自绘卡。

### 4. 来源分组
- 每个 `SourceSpec.Id` 对应左栏一个分组，分组键为 `source:<Id>`；
- 分组位置：**排在「其他」下面**；多个来源按显示文本顺序排列；
- 来源分组只贡献「当前委托」计数，**不计入「可完成」**。

### 5. 计数口径
- 「当前委托」= 原版物品委托数 + 框架委托数；
- 「可完成」= **只统计原版物品委托**中当前可交付的数量（按玩家持有物品判定）。

### 6. 面板节点命名（内部约定）
本 mod 注入的节点统一带 `rb_` 前缀：

| 节点 | 作用 |
|---|---|
| `rb_viewport` | 自建视口（遮罩 + 自建 `ScrollRect`） |
| `rb_content` | 可见内容容器（双列 `GridLayoutGroup` + 高度自适应） |
| `rb_cell_<n>` | 单元格（每张卡一个槽位） |
| `rb_fw_<key>` | 框架委托卡 |
| `rb_rail` | 左栏外框 |
| `rb_rail_view` / `rb_rail_sbar` | 左栏滚动区 / 左栏滚动条 |
| `rb_scrollbar` | 右侧滚动条（克隆原版） |
| `rb_hint` | 空列表提示条 |

作用：
1. **标识归属**：接管与还原时只处理这些节点，不碰原版与别人的对象；
2. **供适配器排除**：例如扫描外来卡时跳过 `rb_fw_`；
3. **便于排查**：层级里一眼可辨认。

这些名字属于**内部实现约定**：可以依赖，但不保证跨大版本不变。

## 三、本 mod 可用的接口

命名空间 `PenRequestUI`，静态类 `CommissionApi`。

### 1. 方法

| 成员 | 签名 | 说明 |
|---|---|---|
| `IsAvailable` | `bool` | 本 mod 是否已启用（未装/未启用为 `false`） |
| `Register` | `bool Register(string modId, CommissionSpec spec)` | 注册单条固定委托 |
| `RegisterSource` | `bool RegisterSource(SourceSpec source)` | 注册带名字的动态来源（推荐） |
| `RegisterSource` | `bool RegisterSource(string modId, Func<IEnumerable<CommissionSpec>> source)` | 简单来源（用 modId 作来源名） |
| `Unregister` | `void Unregister(string modId, string commissionId)` | 取消单条 |
| `UnregisterAll` | `void UnregisterAll(string modId)` | 取消该 mod 的全部注册 |
| `RequestRefresh` | `void RequestRefresh()` | 请求重绘（会延迟合并，不在调用栈内同步重绘） |

### 2. `SourceSpec`

```csharp
public sealed class SourceSpec
{
    public string Id;                                  // 稳定来源 id，对应左栏分组 source:<Id>
    public Func<string> DisplayName;                   // 分组显示名（跟随语言）
    public Func<IEnumerable<CommissionSpec>> Snapshot; // 每次刷新调用一次；纯查询、无副作用
}
```

### 3. `CommissionSpec`

结构化字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `Id` | `string` | 该来源内唯一 |
| `Title` | `Func<string>` | 必填 |
| `Description` | `Func<string>` | 描述 |
| `FactionId` | `Func<string>` | `FACTION_*`；空/非法 → 「其他」分组 |
| `RequesterName` | `Func<string>` | 本 mod 会拼成原版「来自 xx」 |
| `DaysLeft` | `Func<int>` | 剩余天数；`<0` 不显示 |
| `CreditReward` | `Func<int>` | 信用点奖励（显示用） |
| `ReputationReward` | `Func<int>` | 声望奖励（显示用） |
| `PreviewItemId` | `Func<string>` | 可选：用原版物品图标做预览 |
| `IsReady` | `Func<bool>` | 条件是否满足（按钮可点与否）；必须纯查询 |
| `StateLabel` | `Func<string>` | 可选：状态文案（显示在"需求"行） |
| `ButtonLabel` | `Func<string>` | 可选：按钮文字（默认沿用原版） |
| `Submit` | `Action<string>` | 点击按钮触发（参数 = `Id`） |

逐字覆盖字段（优先级高于结构化字段）：

| 字段 | 说明 |
|---|---|
| `TitleText` / `DescriptionText` / `RequesterText` | 直接给最终整段文字 |
| `DurationText` / `RequirementText` / `RewardText` | 直接给"剩余时间 / 需求 / 奖励"整行（多行用 `\n`） |

带结果的动作回推（优先级高于 `Submit`）：

```csharp
public Func<string, string> SubmitJson;   // 返回 {"ok":true,"code":"ok","message":""}
```

- `ok = true` → 本 mod 延迟重绘一次；
- `ok = false` → 只记日志、**不重绘**（由你在业务完成后自行 `RequestRefresh()`）；
- 抛异常 → 记 `framework submit failed`，不重绘。

### 4. 约束

- 所有 `Func` 必须**纯查询**（渲染时可能一帧调用多次）；
- 单个来源最多 **200** 条，超出丢弃并告警；
- 注册方被禁用/卸载后，其条目自动不显示；
- `RequestRefresh()` 会把同一帧内的多次请求合并成一次重绘。

## 四、两种接入方式

### 方式 A：编译期接入（推荐，最稳）

`manifest.xml` 里**不要**写死依赖（见第五节），编译期引用本 mod 的 DLL，运行时先判可用再注册：

```csharp
PenRequestUI.CommissionApi.RegisterSource(new PenRequestUI.SourceSpec
{
    Id = "my_mod.commissions",
    DisplayName = () => "我的委托",
    Snapshot = BuildSpecs
});
```

### 方式 B：抓取式适配（对方不该改代码时）

对"往 `gridLayout` 里塞自绘卡"的 mod：由**独立的适配器 mod** 在
`PCUIManager.OnChange` 之后扫描这些卡、抄下文本与 `acceptButton.onClick`，再以 `SourceSpec` 注册给本 mod。

要点（按实际适配经验总结）：

1. **时机**：在 `PCUIManager.OnChange` 的 Postfix 里排一次延迟抓取（约 0.05s），等对方把卡片建完；
2. **只认该认的卡**：`StoreRequestElement` 且 `storeRequest == null`，且 GameObject 名字**不以 `rb_fw_` 开头**
   （后者是本 mod 渲染的框架卡，必须跳过）；
3. **只读不写**：只读取文本字段与 `acceptButton.onClick`（`UnityEvent`），
   **不要**改对方的 `activeSelf`、不要 reparent、不要销毁对方对象（本 mod 接管期间原版 grid 本身不可见）；
4. **文案来源要确定**：按钮文字优先按对方自己的取法读取（例如"按钮自身的标签 TMP"），
   读不到时按该 mod 的取值语义给固定兜底值，避免落到原版默认文案；
5. **去抖**：对抓取结果算一个内容签名，签名变化才 `RequestRefresh()`；同帧/连续多帧的变化合并成一次；
6. **失败即回落**：抓不到（面板未就绪、对方未渲染）时**保留上一轮数据**，不要清空；
7. **反注册**：适配器被禁用时调用 `UnregisterAll`，让条目立即消失。

## 五、如何编写"可选兼容"（没有本 mod 时保持原版表现）

这是最重要的一节。目标：**装不装本 mod，都不改变原版与你自己 mod 的表现**。

### 0. 先确认你是哪类接入者

| 类型 | 特征 | 是否声明 `<Prerequisites>` |
|---|---|---|
| **通用 mod** | 与本 mod 只是"可选共存"（有自己的完整体验，装不装本 mod 都能玩） | ❌ 不要声明，按本节 1–5 做可选接入 |
| **专用适配器** | 为"本 mod + 某个特定 mod"而生：宿主缺失时它本身没有意义 | ✅ 可以声明 `<Prerequisites><Mod>Pen_mod_Request_UI</Mod></Prerequisites>` |

> 即使是专用适配器：**调用处仍然要 `try/catch`**（宿主被用户禁用时不应抛异常），
> 并且注册前必须同时判断 `ModHelper.IsModRunning("Pen_mod_Request_UI")` 与 `PenRequestUI.CommissionApi.IsAvailable`。

### 1. 通用 mod：不要强制依赖
- **不要**在 `manifest.xml` 写 `<Prerequisites><Mod>Pen_mod_Request_UI</Mod></Prerequisites>`；
- 把它当**可选依赖**：存在则接入，不存在则走你自己的原有逻辑。

### 2. 所有调用都要能安全失败

编译期引用了本 mod 的 DLL，但玩家可能没装 → 首次 JIT 到该类型时可能抛 `TypeLoadException`。
因此**每一个调用点都包 `try/catch`**，并把"失败"当作"没有本 mod"；注册前必须同时判断
`ModHelper.IsModRunning("Pen_mod_Request_UI")` 与 `PenRequestUI.CommissionApi.IsAvailable`：

```csharp
private const string HostId = "Pen_mod_Request_UI";
private bool _hostBound;

public void OnEnable()
{
    TryBindHost();          // 失败就什么都不做：保持你自己原有的界面与行为
}

private bool TryBindHost()
{
    try
    {
        if (!ModHelper.IsModRunning(HostId)) return false;
        if (!PenRequestUI.CommissionApi.IsAvailable) return false;

        PenRequestUI.CommissionApi.RegisterSource(new PenRequestUI.SourceSpec
        {
            Id = ModContext.Id + ".commissions",
            DisplayName = () => "我的委托",
            Snapshot = BuildSpecs
        });
        _hostBound = true;
        return true;
    }
    catch
    {
        _hostBound = false;   // 没装本 mod / 版本不符 / 任何异常 → 回落
        return false;
    }
}

public void OnDisable()
{
    if (!_hostBound) return;
    try { PenRequestUI.CommissionApi.UnregisterAll(ModContext.Id); } catch { }
    _hostBound = false;
}
```

### 3. 回落原则（没接上时）

- 不隐藏自己的卡、不修改原版布局、不改动任何数据；
- 不要"因为检测失败就禁用自己"——按原版/你自己的方式继续运行即可；
- 如果你们的 UI 与委托面板无关，本 mod 存在与否都应当无感。

### 4. 如果你是通过往 `gridLayout` 里塞卡来实现界面的

- 本 mod 接管面板时，`gridLayout` 是隐形数据区 → 你的卡**不会显示**；
- 想共存，只有两条路：
  1. 改为走第三节的接口，让本 mod 渲染你的数据（推荐）；
  2. 写独立适配器，把数据抓出来交给本 mod（做法见"四、两种接入方式 → 方式 B"）；
- 本 mod 关闭后，`gridLayout` 恢复可见，你的卡会照原样显示——所以**不要缓存本 mod 创建的节点引用**。

### 5. 不要依赖的东西

- 不要依赖 `rb_*` 节点（内部约定，见第二节第 6 小节）；
- 不要假设 `gridLayout` 的父级（接管期间它被移进 `rb_viewport`，关闭后还原）；
- 不要 reparent 原版对象、不要改原版 `StoreRequestElement` 的数据；
- 不要在 `OnChange` 之后异步读面板再长期持有引用（面板会重建卡片）。

## 六、本 mod 对面板做了什么（判断冲突用）

接管期间：

1. 原版 `gridLayout` 移入 `rb_viewport`，并加 `CanvasGroup(alpha=0)` → 隐形数据区；
2. 停用原版 `ScrollRect`、隐藏原版滚动条，改用自建滚动（滚动条为原版克隆）；
3. 新建 `rb_content`（双列 `GridLayoutGroup`）承载所有可见卡；
4. 原版物品委托卡从 `gridLayout` 搬进 `rb_cell`（居中、等比缩放）；
5. 新建左栏 `rb_rail`（来源/派系筛选、计数、滚动）与 `rb_hint`（空列表提示）；
6. 把面板上的按钮（关闭等）提到最前，避免被新节点遮挡。

关闭本 mod 时依次：卡片搬回 `gridLayout`（恢复 1:1 缩放与锚点）→ 移除 `CanvasGroup` → 销毁 `rb_content`/`rb_cell`/`rb_rail`/`rb_viewport`/自建滚动条 →
还原 `gridLayout` 的父级、锚点、`GridLayoutGroup` 参数、原版 `ScrollRect` 与滚动条状态。

## 七、Harmony 补丁

| 目标 | 类型 | 作用 |
|---|---|---|
| `PCUIManager.OnChange` | Prefix + Postfix | Prefix：清理失效条目；Postfix：接管面板结构并同步卡片 |
| `StoreRequest.HandleMinorScriptedRequest` | Prefix | 修正原版剧本委托的日期判定（可在配置关闭） |
| `StoreRequestElement.OnClick` | Prefix | `storeRequest == null` 时跳过原版交付逻辑（防止空引用中断点击） |

与其它 mod 的关系：它们若也 patch `PCUIManager.OnChange`，顺序取决于 Harmony 优先级；
本 mod 的接管逻辑不依赖对方是否先运行，但请在改动卡片层级前确认本 mod 是否已接管（判断 `gridLayout` 是否含 `rb_viewport` 祖先）。

## 八、兼容矩阵

| 其它 mod 类型 | 结果 | 说明 |
|---|---|---|
| 数据类（往 `PlayerStore.storeRequests` 加真 `StoreRequest`） | ✅ 开箱兼容 | 走原版卡路径：包裹、装饰、筛选、可完成计数 |
| 框架类（调用本 mod 接口注册委托） | ✅ 官方方式 | 见第三节 |
| UI 注入类（往 `gridLayout` 塞自绘卡） | ⚠️ 卡片不显示 | 需改为接口接入，或写适配器 |
| 契约类（如 `board.v1.list/action` + presenter 形式） | ❌ 未实现 | 本 mod 目前不消费此类契约 |
| 行为改写类（patch 原版委托排序/隐藏） | ⚠️ 需验证 | 与本 mod 的重排/隐形 grid 有交互风险 |
| 纯数据/无 UI mod | ✅ 无冲突 | — |

**已知限制**：
1. 本 mod 不提供 `ModHelper` 运行时服务，第三方只能用编译期接口或抓取式适配；
2. 未实现 `board.v1` 之类的契约式对接；
3. UI 注入类 mod 的卡片会因隐形数据区而不显示。

## 十、排错速查

| 现象 | 日志 | 说明 |
|---|---|---|
| 结构是否接管 | `body='…' … content='rb_content' alpha=0` | `alpha=0` 表示隐形数据区已生效 |
| 左栏是否重建 | `rail update n=… created=… removed=…` | 正常应为 `created=0 removed=0` |
| 轻量刷新 | `soft sync: …` / `soft sync: no framework change …` | 框架侧变化时才会重排 |
| 按钮文案 | `button label target='…' '旧' -> '新'`、`locale off on '…'` | 后者表示已关闭该字段的本地化覆盖 |
| 框架条目 | `framework providers=… entries=… skippedNotRunning=…` | 注册来源数量与条目数 |
| 点击提交 | `framework submit id=…`、`action ok|failed id=… code=…` | `failed` 表示提供方返回了 `ok=false` |

## 十一、版本与承诺

- 适用游戏版本：`1.0.*`（见 `manifest.xml`）；
- 本说明描述的是**当前实现**：接口签名、字段名、节点名与配置键都以本文为准；
- `rb_*` 节点名与日志文本属于内部实现细节，可能随版本调整；接口字段会尽量保持向后兼容，破坏性调整会在工坊更新说明中标注。
